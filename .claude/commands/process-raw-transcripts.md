Execute `/process-raw-transcripts [--batch-size N]`:

> [!warning] There is no `--parallel` flag, deliberately.
> Parallelism was removed after the 2026-07-26 rate-limit incident (see step 2). If you are looking for a way to speed this up, the answer is a smaller `--batch-size` run more often, **never** concurrent dispatch.

> [!info] **Model tiering (added, per the 2026-07-26 buglog entry's deferred idea — now actually wired in).** Because this whole batch runs inside one single agent's own sequential conversation (never per-file dispatch, see above), "model tiering" means choosing what model tier to launch *that one orchestrating agent* with, based on the batch's overall composition — not switching models mid-file. Before starting the batch, skim the queued files' likely signal density (channel history, title length/format, known podcast vs. short-clip patterns — the same signals `/youtube-channel`'s tiering write-up already uses): a batch that's mostly short/straightforward videos can be run under a lighter/faster model tier; a batch that's mostly podcasts, Huberman-length episodes, or content you expect to flag `signal_density: high` should be launched with Sonnet or higher, since that content needs deeper synthesis, more careful quote selection, and a fuller `## Researchers & Sources Cited` pass. If a batch turns out mixed once the per-file signal-density judgment (step 2 below) actually runs, **the quality bar does not move with the tier** — verbatim-quote verification, the anti-fabrication rule, and the signal-density-scaled depth rules in step 2 are non-negotiable regardless of which tier is processing a given file. A lighter tier is only ever a bet on faster/cheaper *routine* execution for content that was already expected to be light; it is never a license to relax verification on any individual file, including ones that turn out denser than expected. If mid-batch judgment reveals a file needs more synthesis effort than the running tier comfortably provides, still do the work correctly rather than under-serving the note — tiering picks the *default* starting posture for the batch, it doesn't cap what an individual file is allowed to receive.

## 1. Find unprocessed raw files
**Run the dedup pre-pass first, yourself — fixed 2026-08-08, previously documented as "the orchestrator's job, not yours" but no orchestrator ever existed to run it, so `Research/.dedup_candidates.json` was never actually being generated.** Run `python scripts/find_cross_stream_duplicates.py` via Bash before anything else in this step — it's a plain Python script, zero Claude tokens, and only takes a moment. This populates/refreshes `Research/.dedup_candidates.json` so stage 0 of the dedup check below (step 2) has real data to check against instead of silently falling through to the more expensive stage 1 every time.

Read `Research/YouTube/Raw/.processed_ids.json` (create empty if absent: `{}`). Every `*_full.txt` file in `Research/YouTube/Raw/` whose `video_id` (from its own header) isn't yet a key in that file is unprocessed. Default `--batch-size 20` per run if not specified.

**Also run `python scripts/find_repeat_candidates.py`** (added 2026-08-20) — zero-Claude-cost, writes `Research/.repeat_candidates.json`: for every unprocessed item, flags a same-channel existing note it likely already covers (keyword/tag overlap on title, scoped to the same channel only — cross-channel overlap is a different, unrelated citation, not a repeat). See step 2's repeat-content handling below for how to use it.

## 2. Per-video note-writing step, single agent, sequential
**Do NOT dispatch parallel subagents for this step, one per chunk or otherwise** — a real 2026-07-26 incident (see `buglog.md`) hit the account's session rate limit almost immediately from per-file/per-chunk parallel dispatch (81 files fanned out, 1 of 84 agent calls succeeded, the rest failed identically) for zero real output. The proven-safe pattern, used successfully multiple times since, is exactly the opposite: **one single `Agent` call whose own internal tool-call loop works through the whole batch sequentially** (read → dedup check → judge relevance → write note → checkpoint state → next file), all within that one agent's own conversation. If grouping by channel is useful for concept-linking coherence, do it as an ordering choice within the single sequential loop, not as a basis for parallel dispatch. This overrides any general "parallel subagents are appropriate" instinct — it is not appropriate here, specifically because of the documented incident above.

- Read the raw file's header (metadata) and body (the transcript itself).

- **Long transcripts (real bug found 2026-08-22, first large-scale batch): the raw body is stored as ONE giant single line with no internal newlines, and the Read tool's offset/limit is line-based — it hits a hard wall on the very first read attempt for anything over ~25K words (multi-hour Attia/Huberman/RP-length episodes).** Do not silently sample a percentage of a long file and write the note anyway — a real incident did exactly this (17-20% coverage, disclosed in-note but still left two Tier-1-person episodes permanently marked "done" on partial reads). Instead: run `python scripts/chunk_long_transcript.py "<raw_file_path>"` first — it splits the body into numbered, Read-tool-sized part files under `.chunks/<video_id>/` (split on sentence boundaries, verified byte-exact reconstruction, raw file itself never touched), then `Read` each part in sequence to get 100% of the actual content before writing the note. Only skip this step for files short enough that a normal `Read` already covers the whole body in one call.

- **Dedup check, three-stage (stage 0 added 2026-08-04 — moves the cheap comparison out of Claude entirely).** The cross-stream duplicate rate (YouTube vs. podcast, especially for "Essentials"-style episodes) has run 30-70% of a batch in recent runs, and a title-only check was previously found unsafe (many episodes share near-identical titles across genuinely different underlying content) — but reading both full transcripts for every candidate is the most expensive single operation in this whole command. Three stages, cheapest first:
  0. **Pre-computed cache (free, zero Claude tokens):** `scripts/find_cross_stream_duplicates.py` — run by you, in step 1 above, before this loop starts — writes `Research/.dedup_candidates.json` — a metadata-only comparison (title fuzzy-match + file-size-as-duration-proxy) across every currently-unprocessed file against every already-written note on the other stream. **Check this file first, by the current file's `video_id`/`episode_guid`.** A `"confidence": "high"` entry can be trusted directly — skip with no further check. A `"confidence": "check"` entry still needs stage 2 below, but you already know which specific note to compare against, so the spot-check is targeted rather than a search. Absence from this file means the script found no metadata match — proceed to stage 1's own inline comparison (the file may have been collected after the script last ran).
  1. **Metadata pass (cheap, in-agent fallback):** if stage 0 didn't cover this file, compare its title, duration, and published/collected date against the other stream's `.processed_ids.json` entries and existing written notes' frontmatter directly (no body read required). If title similarity is low AND duration differs by more than ~20%, it is **not** a duplicate — skip straight to the relevance check below, no content read needed.
  2. **Content spot-check (only when stage 0/1 is ambiguous):** read a bounded sample from each candidate — the first ~500-1000 words is usually enough to confirm or rule out the same underlying recording — rather than the full transcript. Only escalate to reading both files in full if the sample itself is inconclusive (e.g., both start with a generic intro). This preserves the full-read fallback for genuinely ambiguous cases; it just stops treating every candidate as one by default.
  - If confirmed duplicate: mark `processed_ids[video_id] = {"status": "skipped-duplicate-of-<youtube|podcast>"}`, no note written, move to the next file.

- **Repeat-content check** (added 2026-08-20 — Ross's explicit refinement: **never skip, only calibrate effort**, distinct from the dedup check above, which finds the *same recording* published twice; this finds a *different* video from the same creator that likely covers ground they've already covered). Look up this file's `video_id` in `Research/.repeat_candidates.json` (generated in step 1). If flagged (`likely_repeat_of` points at an existing same-channel note): still write a full note for this video, same as any other — but apply the vault's existing content-fidelity discipline (same framing as the resistant-starch/content-fidelity-remining precedent, development.md's 2026-08-17 "Content-fidelity sweep" entry): a **fast cross-check** that claims overlapping with `likely_repeat_of` still match what's already documented, then concentrate real extraction effort on identifying whatever this video adds that the existing note doesn't already have. A `"high"`-confidence flag just means you can lean on the shortcut with more trust; `"medium"` warrants a bit more skepticism that it's genuinely a repeat before doing so. A video that turns out to add nothing new is still a real, reportable finding for the batch summary, not a reason to write a thinner note than its actual signal density warrants.

- **Relevance check** (same as `/youtube-channel` step 7.4): title/description first, transcript skim if ambiguous. Discard off-topic videos - mark `processed_ids[video_id] = {"status": "skipped-irrelevant"}`, no note written.

- **Signal-density flag, and scale note depth to it (added 2026-08-04).** For every relevant, non-duplicate video, judge the ratio of substantive/citable content to total runtime — same method as `/youtube-channel` step 4.5 — and set `signal_density: high | mixed | low` in the note's frontmatter. This isn't just a record; **it sets how much writing effort the note gets**, since a large fraction of tokens in recent batches went into full six-section notes for videos with only a few minutes of real substance:
  - **`high`**: full treatment — all six sections below, 3-5+ verbatim quotes, full Themes & Topics and Worth Following Up On.
  - **`mixed`**: normal `## Key Points`, but trim `## Notable Quotes` to 1-3 of the strongest verbatim quotes rather than exhaustively collecting them, and keep `## Themes & Topics`/`## Worth Following Up On` to the genuinely load-bearing items only.
  - **`low`**: compact note — `## For future Claude`, `## TL;DR`, a short `## Key Points` (2-4 bullets), at most 1 verbatim quote if one is genuinely notable (omit the section entirely if not), and skip `## Themes & Topics`/`## Worth Following Up On` unless something specific is actually worth flagging. **Never trim `## Researchers & Sources Cited`** — that section is cheap relative to the rest and feeds the Web graph regardless of how dense the surrounding content is.
  - This is a depth control, not a relevance gate — a `low`-density video is still real content and still gets a note; it just doesn't get the same token budget as a dense one. Do not use `low` as a backdoor way to reclassify something as `no-substance`; that status is for genuinely empty/gated content (see `buglog.md`'s AMA-preview-segment example), not merely thin content.
  - **This is also the signal that should have driven the batch's model-tier choice up front** (see the model-tiering callout above) — a run turning out heavier on `high`-density files than expected doesn't change the depth/quote/anti-fabrication rules for those files, it's just useful information for how to compose the *next* batch's tier.

- If relevant: body structure per the signal-density scaling above, based on `/youtube-channel` step 6 (`## For future Claude`, `## TL;DR`, `## Key Points`, `## Notable Quotes` - verbatim from the raw transcript text, never paraphrased - `## Themes & Topics`, `## Worth Following Up On`). Exclude promotional material from concept extraction per the same rules. Frontmatter carries over `transcript_source` from the raw file's header if it says `local whisper`, plus `type: youtube`, `cost-usd: 0`, `signal_density: high|mixed|low`, etc.

> [!warning] **A quote can be textually verbatim and still be nonsense** — for any file with `transcript_source: whisper-local` (or the raw header says `transcript_method: local whisper`), local-whisper transcription reliably mangles uncommon pharmacological/scientific/proper-noun terms it doesn't recognize. Real confirmed example (2026-08-28 A/B pipeline test, see `development.md`): a transcript literally reads "I'm running 250 tests, DHA and pregnant along" — almost certainly a garbled "DHEA and Pregnenolone." Copying that string into `## Notable Quotes` would be an exact substring of the source (passes any mechanical verbatim check) but presents the *transcription tool's* error as if it were the speaker's own words, stated authoritatively in a blockquote. Before putting any quote from a whisper-transcribed file into `## Notable Quotes`, read it in context and confirm it reads as coherent prose. If a term looks garbled: prefer a cleaner nearby quote covering the same point instead, or fold the point into `## Key Points` in your own words rather than quoting the garbled transcription verbatim. Never silently "correct" the quote text to what you think was actually said — that misrepresents the source in the other direction.
- **Research & connections extraction (feeds the Web)**: while reading the transcript, separately watch for any real, identifiable named individual referenced as a source of expertise - an interviewee, a cited researcher, a study author, someone credited for a claim (not passing mentions, not "some studies show"). Add a `## Researchers & Sources Cited` section listing each one plus what claim/study they were cited for. For each name not already a `People/` note (dedup by name + any known handle, same rule as `/web-expand`), create a stub `People/` note (`discovered_via: "[[<this note>]]"`, `derived_tier` one hop out from whichever anchor/channel this video belongs to, `connection_type: "interview"` or `"influence"` per how they were referenced) and add it to a running "new people to research" list for this batch. This is exactly `/web-expand`'s discovery step, applied inline per-video instead of requiring a separate pass - the point is that no researcher/source mentioned in ingested content goes untracked as a potential Web connection.
- Save `Research/YouTube/YYYY-MM-DD - <title-slug>.md`, mark `processed_ids[video_id] = {"status": "ok", "note": "<path>", "signal_density": "high|mixed|low", "people_discovered": ["<name>", ...]}` in the shared state file.

**State writes**: because the loop is sequential and single-agent, there is no write race to design around - checkpoint `.processed_ids.json` after **every single file**, not at the end of the batch. That is what makes an interrupted run (usage limit, crash, reboot) lose at most the one file in flight instead of the whole batch. Still read-modify-write it (read fresh, merge, write) rather than overwriting wholesale, since a Stage-1 collector may touch the same directory concurrently.

## 3. Sequential concept-linking pass (after the whole batch finishes)
This step does NOT parallelize - it needs a holistic view across everything the whole batch touched, same as `/youtube-channel` step 9: aggregate concepts touched, actively absorb substantive content into `Concepts/` notes (rewrite/deepen, don't just link), mark absorbed video notes with the `> [!info]` pointer, cross-link related concepts, identify and fill real gaps via `/research`, flag contradictions with the normal `[!contradiction]` callout. **This step must actually complete or be cleanly resumed — never let a batch finish note-writing without also finishing concept-linking.** The `[!info]` banner is the vault's real manifest of "already absorbed"; a batch that skips this step silently creates the exact backlog a 2026-08-08/09 session had to spend four separate expensive catchup passes reconciling.

**Token-efficiency rules for this step and for any standalone Concepts-catchup pass (added 2026-08-09, real lesson from that session):**
- **Check `Research/.concepts_absorbed.json` first** (rebuild via `python scripts/build_concepts_absorbed_manifest.py` if it looks stale) — skip any note already listed rather than re-reading it or re-grepping Concepts/ to check. This one file replaces what used to cost a real read/search per note.
- **Default to `signal_density: high` (and usually `mixed`) only** when doing a catchup/reconciliation pass across many existing notes — skip `low` entirely unless specifically asked to include it. Low-density notes are the ones least likely to have anything Concepts-worthy, and this is now checkable from frontmatter alone, no read required.
- **A note with no `signal_density` field and a channel/title matching a confirmed-low-value pattern** (e.g. short workout-demonstration clips) should get `signal_density: low` set (see `scripts/tag_low_value_notes.py` for the precedent — Kinobody and several boxing/MMA-technique channels were confirmed low-value by direct sampling, not assumed) rather than re-sampled by a fresh agent each time.
- **Model tiering**: the mechanical part of a catchup pass (read a note, check whether a claim already exists, append a citation) doesn't need the primary model — only escalate to it for genuine judgment calls (is this actually novel, does it contradict something, does it warrant a new Concept note). When dispatching a catchup batch via the `Agent` tool, consider a cheaper model for the bulk pass.

Also merge every processed file's `people_discovered` entries into one batch-wide list, dedupe against existing `People/` notes exactly as `/web-expand` does (best tier/hop path wins), and finalize each new stub note's frontmatter. Do not run full literature/channel research on newly-discovered people in this same pass - that's `/web-expand`'s job on a follow-up run; this step only ensures they exist as tracked stubs so nothing is dropped.

## 4. Rollup
Same as `/youtube-channel` step 10 - update the relevant `Synthesis/Channels/<channel> - Channel Rollup.md` for each channel touched this batch, and `Synthesis/Channels to Follow.md`.

## 5. Summary
Batch size, relevant/discarded/failed split, **signal-density breakdown among relevant videos (high/mixed/low counts)**, **dedup breakdown (how many resolved at the cheap metadata stage vs. needed a content spot-check vs. needed a full-transcript read)**, **repeat-content breakdown (how many videos were flagged by `find_repeat_candidates.py`, how many actually turned out to add new material vs. genuinely nothing new)**, concepts created/deepened, gaps filled, new `People/` stubs discovered this batch (names + who to `/web-expand` next), rollup notes updated, and how many unprocessed raw files remain in `Research/YouTube/Raw/` for a future run.

**Anti-fabrication:** same rules as every other ingestion command in this vault - verbatim quotes only from the actual raw transcript text, never invent a gap-fill fact. "Verbatim" means exact-substring-of-the-source, not "trust it's coherent" - see the whisper-mangled-quote warning above.
